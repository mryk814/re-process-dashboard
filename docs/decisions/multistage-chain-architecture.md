## 背景

現行の本番タスクは、入力群（composition / process / categorical / heat_pattern）から出力へ一段で写す縦スライスである。
一方、粉体を配合して作る材料（溶接材料、フラックス入りワイヤ、粉末冶金など）では、判断対象が次のように多段になる。

```text
[原料 slot × K]  --A: 線形（決定論）-->  [材料成分 数十]
                                             |
                             [溶接条件（入熱・ガス・極性…）]
                                             v
                                    --B: 学習モデル-->  [溶着金属成分 十数]
                                             |
                                 [試験条件（試験温度など）]
                                             v
                                    --C: 学習モデル-->  [特性（TS/YS/伸び/吸収エネルギー/脆性破面率/腐食速度）]
```

この構造には、現行契約が前提にしていない性質が四つある。

1. 選択肢としての原料が数百あり、一つの候補が使うのは10〜20である。入力が疎で可変長になる。
2. 原料は群（用途・調達可否）を持ち、「この群からはこれを使う」という選択制約が候補の妥当性を決める。
3. 中間量（溶着金属成分）が実測できる。つまり中間ノードに教師データがある。
4. 利用者の関心が段ごとに分かれる。原料をどう決めるか、どの成分を狙うか、どんな特性が出るか、のいずれもが判断対象である。

## 方針

### 1. 原料を予測モデルの変数にしない

モデルB・Cの入力は成分（数十次元）であり、原料ではない。原料はAで成分へ潰す。

- 原料マスタに1行追加してもモデルの入力次元は変わらないため、新しい原料の追加で再学習が不要になる。
- 単段モデルで原料を直接説明変数にすると、原料追加のたびに入力契約とモデルが同時に壊れる。多段にする最大の実利はここにある。

### 2. 候補の正本は疎表現とする

候補の配合は `[(原料ID, 配合比[%]) × K]` の可変長リストで保持する。数百次元の密ベクトルは、特徴量化の直前に作る派生物として扱い、永続化・差分表示・XLSX入出力・UIはすべて疎表現側で行う。

### 3. 群と調達可否はDesign Space側の制約とする

「群Xから最大2点」「群Yの合計は5〜12%」「A/B/Cのいずれか1つ」「調達区分が常用の原料だけ」といった条件は、タスク契約ではなくDesign Space Definitionが担う。
既存の `CompositionTotalDefinition`（`balance_path` 付き）と `RelationalConstraint` の延長線上にあり、選択制約（集合の濃度制約）だけが新しい語彙になる。

### 4. 成分に落ちない原料属性の口を最初から用意する

粒度、供給状態、同一成分でも歩留まりが異なる、といった効果は成分ベクトルでは表せない。
これらは「原料由来の補助特徴」として少数だけBの入力へ流す。後付けするとAの線形性が崩れるため、最初から別枠として宣言する。

### 5. Aも Model Package として扱う

原料→成分の行列変換は、学習モデルではないが `deterministic-linear` runtimeのModel Packageとして allow-list へ載せる。
これによりAの版管理・検証・digest記録・UI表示が学習モデルと同じ経路に乗り、Chain実行基盤に例外分岐が生まれない。フープ（外皮）と充填率の合成も同じ線形変換に含められる。

### 6. Chainは binding で表す。入口は増やさない

各段は現行 `TaskDefinition` とほぼ同じ形のまま残し、新しく足すのは **binding**（ある段の入力フィールドが上流段のどの出力であるかの宣言）だけとする。

当初は「原料から」「材料成分から」「実測溶着成分で固定」を切り替える entry point を持たせる案だったが、モックアップで確認した結果、**入力モードとしては採らない**。

- 「材料成分から」は、実現する配合が決まらないため判断が閉じない。成分だけを動かしたい要求は、目標成分からの逆算（方針9）で満たすほうが素直である。
- 「実測溶着成分で固定」は、入力モードではなく**実測照合**である。分析結果が出た後に予測と実測を突き合わせる作業であり、既存の実測照合の側で扱う。

v1のChainは「原料から」の一本とする。

### 7. 中間実測を使い、精度を二つに分けて出す

段ごとに独立して学習する。Cは実測溶着成分で、Bは実測溶着成分を目的変数として学習する。学習行数や母集団が段ごとに違ってよい。
表示する精度は次の二つを分ける。

- **段単体精度**：実測の上流値を入れたときの各段の精度。
- **通し精度**：上流の予測値を通したときの精度。必ず悪化する。

この差が「どの段が効いているか」の判断材料になる。予測値と実測値を混同させないという既存原則の多段版として扱う。

### 8. 不確かさの伝播は段階的に導入する

- v1：点推定を通し、各段の不確かさを併記する。段をまたいで合成しない。
- v2：上流の事後分布からサンプリングして下流へ流す。runtime capabilityにサンプリング能力があるかで分岐させる。

### 9. 目標成分から配合への逆算は学習モデルを使わない

特性からの逆問題は解かない。前向き探索と制約（既存の範囲探索・Design Space・LHS）で答える。
一方、**目標成分から原料配合への逆算は、Aが線形であるため線形計画として厳密に解ける**。

```text
minimize  コスト（または基準配合からの距離）
s.t.      M · x = 目標成分（許容幅つき）
          Σx = 100,  x ≥ 0
          群制約・使用可能原料制約・上下限
```

数百原料でも高速に解け、「その成分を実現する配合が存在しない」ことも判定できる。学習モデルは不要である。

### 10. 版の固定と再計算

- **Chain Revision** は各段のModel Package digestの組である。予測スナップショットにはChain Revision全体を残す。
- 再計算は content hash によるメモ化とし、入力が変わった段より下流だけを再実行する。

## 画面と操作の方針

数百の原料を設計に使う画面は、契約と同じくらい難しい。実現方式を先に固定しておく。

### 前提：入力面の性格が変わる

現行の候補入力は、タスクが宣言した固定のフィールド集合を持つ「フォーム」である。
配合は候補ごとに行数と行の顔ぶれが変わるため、入力面は「明細（line item）」になる。
フォームの延長として作らない。

### 合計100%の扱い

20行の数値がすべて独立に編集でき、かつ合計を100%に保てという要求は、そのままでは操作不能になる。次の二つを組み合わせる。

- **残部原料を1点指定する**。編集した差分はその行が吸収する。Design Spaceの `balance_path` を画面の第一級の概念として出す。
- **行ロック**。ロックした行は再配分の対象から外す。残部が下限に達した場合は、警告を出して自動では崩さない。

非ロック行を比例再配分する方式は、触っていない行が動くため採らない。既定は残部吸収とする。
合計が満たせない状態は、自動修正せずエラーとして残す。候補は不成立のまま保存できてよい。

### 原料の選び方

- 追加操作は **群 → 役割 → 銘柄** の三段とし、初期状態で `廃止予定` を隠す。`試作限定` は印を付けて表示する。
- 慣れた利用者向けに、原料コード・名称・主成分でのインクリメンタル検索を併置する。三段の選択だけを強制しない。
- 最頻の操作は新規追加ではなく **銘柄の置き換え**（同じ原型の別銘柄への差し替え）である。行の操作として独立して置き、調達区分、単価、粒度、主成分を並べた比較を出す。
- そのため **原料マスタは「原料種類」を列として持つ必要がある**。名称からの推測で置換候補を決めない。置換候補の集合が契約として定まっていることが、この操作が成立する条件である。
- 配合はすでに手元のExcelにある。**原料コード列と比率列の貼り付け取り込み**を最初から用意する。1点ずつ選ぶUIだけでは実務で使われない。

### 見せる層を三つに限る

1. 配合明細（10〜20行の疎な表）
2. 派生した材料成分（非ゼロのものだけ。既定は基準候補との差が大きい順の上位、全表示は明示操作）
3. 予測される中間成分と特性

31成分や数百原料を一度に並べない。並べ替えの既定は「差の大きい順」であり、原料コード順ではない。

### 候補比較は和集合と差分

候補ごとに原料集合が違うため、比較表は行の和集合を作り、含まれない候補のセルは空を明示する。
既定は「差のある行だけ」を表示し、全行表示は明示操作とする。これがないと比較表が数百行になる。

### 段の可視化と再計算

- 画面上部に A→B→C の**ステージレール**を常設し、各段の状態を示す。
- **下流の再計算は自動を既定とする。** 当初は「上流を編集したら下流を古い状態にして明示実行させる」案だったが、モックアップで確認した結果、体験として自動更新のほうが素直である。手動を既定にする根拠は「重いかもしれない」だけであり、それは実測してから決める（憲章の「実測して遅い箇所だけ改善する」）。
- 自動更新が破綻するのは次の場合だけなので、**段の単位で**明示実行へ落とす。全段をまとめて手動にしない。
  - ある段の推論が体感できるほど遅い。→ その段だけ明示実行にする。
  - 不確かさのMonte Carlo伝播を行う。→ 点推定は自動、分布は明示実行と粒度を分ける。
  - 編集の連打で計算が積み上がる。→ 編集停止後のデバウンスと、古い実行の打ち切りで処理する。
- 自動にしても**段ごとの鮮度（最新／再計算中／古い／失敗／実測で固定）は内部構造として残す**。失敗した段や実測で固定した段を区別するのに必要であり、明示実行へ落とす切り替えもこの構造の上で行う。
- 段Aは線形なので常に即時更新とする。

### コストを判断面に出す

原料マスタが単価を持つため、配合コストは追加の学習もデータ収集もなく出せる。

- 行ごとの金額寄与と、その配合コストに占める割合。少量でも高価な原料が判断対象になる。
- 配合全体の粉のコスト。候補比較にも行として並べる。
- 逆算（方針9）の目的関数と同じ量であり、先に画面へ出しておくと逆算の結果を読む準備になる。

### 比較表の向き

design-system.md は「候補比較表では候補名を左側に固定し、入力と予測の列を横スクロールする」と定めている。つまり既存は**候補＝行**である。
配合はこの向きでは破綻する。変数（原料）が数百になりうるため、列が数百になる。

**行数が可変なほうを行に置く**、という規則で整理する。

| ブロック | 向き | 理由 |
|---|---|---|
| 配合明細の比較 | 原料＝行、候補＝列 | 行数は原料の和集合で可変、列数は候補数で有界。横長画面とも相性がよい |
| スカラー入力、予測特性 | 候補＝行（既存のまま） | 項目数が固定で少ない |

同じ画面で向きが混ざるが、既存規則の例外ではなく、上の一つの規則で説明できる形にする。

### 逆算のUI

目標成分から配合を求める操作は、結果だけを出すと根拠のない魔法に見える。次を守る。

- 使用可能原料、群制約、目的（コスト最小か基準配合に近いか）を利用者が明示してから実行する。
- 解が出た場合は通常の候補として編集可能な状態へ落とす。読み取り専用の結果で終わらせない。
- 解が存在しない場合は、どの制約が矛盾したかを示す。「解なし」だけを返さない。

### 画面として作らないもの

- 数百行のスプレッドシート的な全原料表。
- 円グラフやドラッグで比率を決める配合エディタ。数値精度が出ず、キーボードで操作できない。
- 最良候補の自動選定や自動最適化のボタン。憲章の対象外を継続する。

### モックアップで確認して決めたこと（2026-07-25）

合成データで実際に計算が動くモックアップを作り、操作して次を決めた。

| 論点 | 結論 |
|---|---|
| 残部吸収 | 採用。編集した差分を残部が吸収する挙動は直感的に働く |
| 下流の再計算 | 自動を既定とする。手動は段の単位で後から落とす |
| 入口の切り替え | 持たない。v1は「原料から」の一本 |
| 基準候補との差の表示 | 採用。理解の手数が明確に減る |
| 上位表示と全表示の分離 | 採用 |
| 候補比較の既定 | 「差のある行だけ」。ただし比較対象は独立した配合ではなく**既存候補からの派生**が主になる |
| コスト表示 | 常時出す |

候補比較で分かった重要な点として、独立した3配合を並べると差分表示がほとんど機能しない。
実際の試行錯誤は「既存候補からの派生」であるため、**候補の作成は派生を主操作とし、派生元を記録する**。

### 実際に触って決める論点

- 残部吸収と行ロックだけで足りるか、比例再配分も要るか。
- 成分表示の既定の並び順を「差の大きい順」とするか「目標に効く順」とするか。
- ステージレールを常設するか、候補比較画面では畳むか。

## 現行契約との差分

| 対象 | 追加が必要なもの |
|---|---|
| `TaskDefinition` | 入力フィールドの binding 宣言 |
| 候補契約 | 疎な `(原料ID, 比率)` リスト型の入力群、派生元候補の記録 |
| 原料マスタ | 銘柄の置換候補を定める「原料種類」列 |
| Design Space | 選択制約（群からの選択数、使用可能集合） |
| Model Package | `deterministic-linear` runtime |
| Dataset Input Profile | 多対多の明細シート（配合明細）を候補入力へ写す規則 |
| スナップショット | Chain Revision（段ごとのpackage digestの組） |
| Project | 1 Project = 1 Task の前提の見直し。崩すのはProject側であり、Task契約側ではない |
| 候補入力UI | 行を増減できる明細エディタ、残部原料、行ロック、貼り付け取り込み、コスト表示 |
| 候補比較UI | 配合明細だけ転置した、行の和集合と差分のみ表示 |
| 画面共通 | ステージレールと、段ごとの鮮度（最新／再計算中／古い／失敗／実測で固定） |

## 段階的な導入順

| Phase | 内容 | 狙い |
|---|---|---|
| 0 | Cだけを単独タスクとして追加（溶着成分＋試験条件→特性） | 現行のTask契約のまま。既存の縦スライス方式にそのまま乗る |
| 1 | `deterministic-linear` runtimeを追加し、Aを Package化 | 線形で検証が容易。Chain実行基盤の試運転になる |
| 2 | Bを追加し、三段をChainとして結線 | ここで初めて binding 宣言を導入する |
| 3 | 不確かさ伝播、目標成分からのLP逆算 | |

## この段階で扱わないもの

- 特性からの逆モデル。
- 段をまたいだ end-to-end 学習。中間実測を捨てることになるため採らない。
- 段の自動探索やグラフの汎用エディタ。Chainは開発者が定義する契約とする。
- アプリ内での学習・ベイズ最適化。憲章の対象外を継続する。
