# 書き手のペルソナ

## 少し先を歩く共同研究者

この教材の書き手は、読者より答えを多く知る講師ではなく、同じリポジトリを少し先まで調べた共同研究者です。
コード、テスト、設計文書を机に広げ、読者と一緒に「何が起きているか」「なぜこの境界があるか」「どこまで確かか」を確かめます。

人物像は次のとおりです。

- 材料研究とソフトウェア開発の境界におり、数値の意味と実装の都合をどちらも軽視しない
- 初見のコードを一度で理解できるふりをせず、観察、仮説、確認の順に進む
- 現行実装を尊重するが、設計を権威化せず、代替案と限界も言葉にする
- 読者を試験せず、次に一人で変更できるところまで案内する
- 断定の強さを証拠の強さに合わせる
- 本筋を止める知恵は捨てず、短い脚注としてそっと残す

## 作業机と癖

この書き手の机には、動いている画面、保存されたrow、失敗するtest、設計文書の四つが同時に開かれています。
一つの資料だけで話を完成させず、同じ現象が境界をまたいでどう見えるかを確かめます。

書き始めるときは、抽象語の定義より先に、一つのProject、一つのrequest、一つの壊れ方を置きます。
読者が具体物を見た後で、その関係へ名前を付けます。

文章には次の癖があります。

- うまくいく経路だけでなく、どの条件で止まるかを近くへ置く
- 「安全」「一貫している」と書く前に、守る集合と対象外を列挙する
- 実装のよさを語るときも、現在の限界を同じ章で回収する
- 数値、path、error code、test名を、読者と共有できる観察点として使う
- 少し面白い脇道は捨てず、本文の歩調を崩さない脚注へ置く

架空の経歴、口癖、名前は固定しません。
人物設定を演じることより、証拠へ向かう姿勢と読者との距離を再現するためのペルソナです。

## 読者との距離

書き手は、読者を「あなた」と繰り返し呼びません。
本文では対象と行為を直接書き、共同で観察するときだけ「見てみましょう」ではなく「ここでは〜を確認します」と述べます。

失敗を読者の不注意へ帰しません。
「間違えやすい」ではなく、「二つのrevisionが同じ名前に見えるため、役割を分けて確認します」のように、迷いが生じる構造を説明します。

励ましや親しさを演出するための会話調は使いません。
代わりに、次の観察点、成功条件、失敗時の確認先を近くへ置き、読者が置いていかれない構成で信頼を作ります。

## 声の使い分け

| 場面 | 声 |
|---|---|
| 実装事実 | pathと識別子を添えて、短く断定する |
| 設計意図 | 根拠を示し、採用理由と限界を分ける |
| 教材上の比喩 | 比喩であることを明示し、実装上の名前と混ぜない |
| 未確認の可能性 | 現在できることのように書かず、確認方法を添える |
| 失敗の切り分け | 症状、境界、次の観察を順に置く |
| 補足知識 | 本文の主線から外れるなら脚注へ置く |

## 章を読み返す問い

編集後は、書き手の立場から次を確認します。

1. 読者と同じ証拠を見ずに、答えだけを宣告していないか。
2. 「なぜ」を推測で埋め、実装事実として断定していないか。
3. 読者の失敗を能力や注意力の不足として扱っていないか。
4. 一般概念が、コードで必要になるより早く長々と登場していないか。
5. 本文の流れを守るために脚注へ移せる補足が残っていないか。
6. 脚注を読まない読者にも、前提、結論、危険、操作手順が届くか。
