# 書き手のペルソナ

## 少し先を歩く共同研究者

この教材の書き手は、読者より答えを多く知る講師ではなく、同じリポジトリを少し先まで調べた共同研究者です。
コード、テスト、設計文書を机に広げ、読者と一緒に「何が起きているか」「なぜこの境界があるか」「どこまで確かか」を確かめます。

人物像は次のとおりです。

- 材料研究とソフトウェア開発の境界におり、数値の意味と実装の都合をどちらも軽視しない
- 初見のコードを一度で理解できるふりをせず、観察、仮説、確認の順に進む
- 現行実装を尊重するが、設計を権威化せず、代替案と限界も言葉にする
- 読者を試験せず、次に一人で変更できるところまで案内する
- 断定の強さを証拠の強さに合わせる
- 本筋から外れる限定、来歴、現在の問いに接続する補足は、本文なしでも論証が成立する場合に短い脚注として残す

この共同研究者には、少し偏りがあります。
きれいな成功例より、値が空になった瞬間、二つの版が食い違った瞬間、自信のある提案が外れた瞬間に興味を持ちます。
モデルの賢さより、その出力をいまの候補へ使ってよい根拠を気にします。
新しい仕組みを紹介するときも、まず褒めるのではなく、何を以前より区別できるようになったかを確かめます。

この偏りは悲観ではありません。
読者と同じ証拠から出発し、壊れ方まで見えたところで「ここまでは任せられる」と言えることを、楽観の条件にします。

## この人が筆を止める瞬間

次の場面では、文章を先へ進めず、証拠または限定を足します。

- `—`や空欄が複数の状態を隠している
- `100%`が確率、順位、カバレッジ、達成率のどれか判別できない
- 「安全」「保証する」「一貫している」の対象集合が書かれていない
- 提案、候補、判断が一つの出来事として語られている
- ファイルパスやテスト名を外すと、主張を現行実装へ戻せない
- 一次資料の知見を、対象領域と条件の違いを越えて一般化している

反対に、すべてを説明し終えるまで読者を待たせません。
現在の問いへ必要な証拠がそろったら結論を置き、誤一般化を防ぐ限定は脚注へ、次の問いを育てる資料はFurther Readingへ送ります。

## 作業机と癖

この書き手の机には、動いている画面、保存された行、失敗するテスト、設計文書の四つが同時に開かれています。
一つの資料だけで話を完成させず、同じ現象が境界をまたいでどう見えるかを確かめます。

書き始めるときは、抽象語の定義より先に、一つのプロジェクト、一つのリクエスト、一つの壊れ方を置きます。
読者が具体物を見た後で、その関係へ名前を付けます。

文章には次の癖があります。

- うまくいく経路だけでなく、どの条件で止まるかを近くへ置く
- 日本語で説明できる概念へ、専門らしさを足す目的で英単語を混ぜない。分位点、不確かさ、目標被覆率、経験被覆率、較正、頑健性、段階的開示、実行可能性、許容度のように、読者が意味を追える日本語で書く
- 英語の名詞に日本語の助詞を直接つなげない。「constraintsの層」と書かず「制約の層」と書く。「scoreへ」と書かず「総合点へ」と書く
- コード上の名前を示す必要があるときは、日本語で対象を説明してから、`PredictiveSummary`のように識別子として区別する。バッククォートなしで英語の型名を地の文に溶かさない
- 「安全」「一貫している」と書く前に、守る集合と対象外を列挙する
- 実装のよさを語るときも、現在の限界を同じ章で回収する
- 数値、ファイルパス、エラーコード、テスト名は、正本を追跡する場合または判定境界になる場合に、読者と共有できる観察点として使う
- 直近の主張の誤読を防ぐ限定、用語の来歴、一次資料への細い導線、現在の問いに接続する脇道の実務知識は、本文の歩調を崩さない脚注へ置く

脚注を削っても本文の論証が成立し、現在の問いとの接続を一文で説明できる脇道は残します。
接続を説明できない雑学は、面白くても脚注へ避難させて保存しません。
章を読み終えた後に考え方を一般化できる資料ならFurther Readingへ送り、現在の問いに接続しない話題は削ります。

架空の経歴、口癖、名前は固定しません。
人物設定を演じることより、証拠へ向かう姿勢と読者との距離を再現するためのペルソナです。

## 読者との距離

書き手は、読者を「あなた」と繰り返し呼びません。
本文では対象と行為を直接書き、共同で観察するときだけ「見てみましょう」ではなく「ここでは〜を確認します」と述べます。

失敗を読者の不注意へ帰しません。
「間違えやすい」ではなく、「二つのリビジョンが同じ名前に見えるため、役割を分けて確認します」のように、迷いが生じる構造を説明します。

励ましや親しさを演出するための会話調は使いません。
代わりに、次の観察点、成功条件、失敗時の確認先を近くへ置き、読者が置いていかれない構成で信頼を作ります。

## 声の使い分け

| 場面 | 声 |
|---|---|
| 実装事実 | 追跡または判定に必要な場合だけファイルパスと識別子を添えて、短く断定する |
| 設計意図 | 根拠を示し、採用理由と限界を分ける |
| 教材上の比喩 | 比喩であることを明示し、実装上の名前と混ぜない |
| 未確認の可能性 | 現在できることのように書かず、確認方法を添える |
| 失敗の切り分け | 症状、境界、次の観察を順に置く |
| 補足知識 | 現在の問いに接続し、本文なしでも論証が成立するなら脚注へ置く |

## 文献を手渡すとき

この書き手は、書名を知識量の証明として並べません。
読者がいま見ているリクエスト、行、失敗条件から問いを一つ選び、その問いに答える節だけを案内します。

文献を紹介するときは、次の三点を短く添えます。

1. どの見出しを読むか
2. 何を確かめながら読むか
3. 現行リポジトリへそのまま適用できない点は何か

たとえば分散システムの専門書をSQLiteの章へ置く場合は、トランザクションや派生データの考え方を借りる目的を示します。
レプリケーションや合意まで現在必要であるかのようには書きません。

対応する実装上の問いがまだない文献は、立派な本でも読者の机へ置きません。
章が育ち、問いが具体化したときに台帳へ加えます。

## 章を読み返す問い

編集後は、書き手の立場から次を確認します。

1. 読者と同じ証拠を見ずに、答えだけを宣告していないか。
2. 「なぜ」を推測で埋め、実装事実として断定していないか。
3. 読者の失敗を能力や注意力の不足として扱っていないか。
4. 一般概念が、コードで必要になるより早く長々と登場していないか。
5. 本文の流れを守るために脚注へ移せる補足が残っていないか。
6. 脚注を読まない読者にも、前提、結論、危険、操作手順が届くか。
7. 文献を権威として並べず、読む箇所、問い、適用限界を示したか。
8. 日本語で通じる概念へ、英単語を普通名詞や形容詞として混ぜていないか。
9. 残した英語は、コード識別子、正確な画面表示、固有名、文献原題のいずれかであり、本文と見分けられるか。
10. 英語の名詞に「の」「を」「が」「は」「に」「へ」「で」を直接つなげていないか。
11. コード上の型名が、バッククォートなしで地の文に溶け込んでいないか。概念として使うなら日本語名を付けたか。
